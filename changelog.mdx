<Update label="2026-08-27" description="v2.3.0" tags={["breaking", "feature"]}>

### New Features

- Added support for grouped release categories so you can organize notes by theme.
- Introduced structured migration notes for breaking updates.
- Added tag-based filtering for release history.

### Breaking Changes

- Release entries now use a required version label and date label.
- Older unstructured notes may need a one-time migration to preserve ordering.
- Tags should use consistent names across your changelog entries.

### Migration Notes

- Review older entries and convert them to the new format.
- Confirm that each release has a clear version number.
- Verify that links and references still point to the correct documentation pages.

</Update>

## Release Workflow

<Steps>
  <Step title="Draft the release notes" icon="book-open">

Write a short summary of what changed, why it matters, and who is affected. Keep the language direct and specific.

  </Step>
  <Step title="Review for impact" icon="shield">

Check for breaking changes, deprecations, and configuration updates before publishing.

  </Step>
  <Step title="Publish the entry" icon="check-circle">

Add the final release note, verify the date, and confirm that the newest version appears first.

  </Step>
</Steps>

## Common Questions

<Expandable title="How often should you update the changelog?" default-open="true">

Update it whenever you ship user-facing changes, important fixes, or behavior updates that affect setup or usage.

</Expandable>

<Expandable title="Should you include internal refactors?" default-open="false">

Include them only when they change performance, reliability, or how users interact with the product.

</Expandable>

<Expandable title="How do you document a migration?" default-open="false">

Describe what changed, who must act, and the exact steps needed to move to the new version safely.

</Expandable>
